# 最重要的開發規則：Incremental Implementation

本專案必須採用「一次只完成一個階段」的開發方式。

**禁止一次完成整個 Agent Runtime。**

你必須嚴格按照階段順序工作。

每次只執行目前被指定的階段。

完成該階段後：

1. 編譯
2. 執行該階段相關測試
3. 修正該階段產生的問題
4. 再次執行測試
5. 確認該階段達到驗收標準
6. 回報：

   * 修改了哪些檔案

   * 為什麼修改
   * 執行了哪些命令
   * 測試結果
   * 是否通過
   * 下一階段準備做什麼

**完成後立即停止。**

不得因為目前階段已完成，就自行繼續實作下一階段。

只有在使用者明確要求「繼續下一階段」後，才能開始下一階段。

# 第二階段：Canonical Core Data Model

這一階段只處理 Agent Core 的核心領域資料結構（不引入 JSON serde、不碰磁碟、不碰 Tool）。

確認並統一核心概念型別：

* Goal
* AgentDecision（Observe, Act(Action), Wait, Finish(FinalTaskStatus)）
* Action（Observe, Execute, Interact, Wait）
* ActionResult（由 Runtime 產生的客觀執行結果）
* Observation（環境證據）
* AgentState（Working Memory）
* ExecutionState（Running, Waiting）
* FinalTaskStatus（Done, Blocked, Impossible, NeedUser）

重要規則：

* **Action 是 Core 的 canonical domain model**，AgentDecision 必須使用 Action。
* **嚴格分離 ExecutionState 與 FinalTaskStatus**，AgentDecision::Finish 必須使用 FinalTaskStatus。
* 本階段不包含 ToolCall 或 ToolResult，ToolCall 屬於後續 LLM wire protocol。

最小必要驗證：

* `cargo check --lib`
* `cargo test --lib core::types`（純記憶體型別構建與狀態轉移測試）

完成後停止。

# 第三階段：Schema Serialization, Strict Validation & State Checkpoint

建立核心資料結構的序列化、嚴格反序列化驗證，以及 Phase 0 最小 Checkpoint 抽象。

範圍：

1. **Serde JSON 實作**：
   * AgentDecision、Action、ActionResult、Observation 的序列化與反序列化。
   * 嚴格解析驗證（無效 enum、缺少欄位時回傳結構化 ParseError，禁止容忍非法輸入）。
2. **Minimal JSON Checkpoint 抽象**：
   * 建立 `CheckpointStore` 抽象介面。
   * 使用 Serde + JSON 檔案保存與載入 `AgentState`。
   * **禁止引入 SQLite 或任何外部資料庫**。

最小必要驗證：

* `cargo test --test schema_tests`（測試合法/非法 JSON 解析）
* `cargo test --test checkpoint_tests`（測試 AgentState 序列化存檔與還原）

完成後停止。

# 第四階段：Deterministic Mock LLM & Fake Runtime

建立純記憶體、無外部副作用的測試替身（Test Doubles）。

範圍：

1. **Mock LLM Provider**：
   * 不依賴真實自然語言模型。
   * 支援腳本化（Scripted Decisions），可依照傳入的上下文與步驟依序回傳固定 AgentDecision。
2. **Fake Runtime**：
   * 純記憶體模擬 Action 執行。
   * 可受控地模擬成功、失敗、timeout、AccessDenied 等情境。
   * 回傳客觀的 `ActionResult` 並轉換為 `Observation`。

最小必要驗證：

* `cargo test --test test_doubles_test`（驗證 Mock LLM 回傳序列與 Fake Runtime 回應）

完成後停止。

# 第五階段：Deterministic Closed-Loop & Event Trace (Phase 0 核心)

在純記憶體環境中跑通 Agent 核心閉環，並具備結構化 Event Trace 與狀態恢復能力。

範圍：

1. **最小 Agent Loop**：
   `Goal -> Observe -> Decide -> Act -> Observe -> Evaluate/Revise -> Verify -> Finish`。
2. **Structured Event Log / Trace**：
   記錄 step, run_id, event_type, payload。
3. **AT-CORE-001 驗收場景實作**：
   * Agent 取得 Goal。
   * Agent 產生 Action。
   * Fake Runtime 故意回傳失敗（Failure Observation）。
   * Agent 收到失敗後，**不直接結束**，而是修改 Hypothesis / Strategy。
   * Agent 採取不同的 Action。
   * Fake Runtime 回傳成功。
   * Agent 執行 Goal Verification。
   * Agent 回傳 Finish(Done)。
4. **Crash → Resume 場景驗證**：
   * 在閉環執行中途呼叫 Checkpoint 保存狀態。
   * 銷毀執行期記憶體 context，從 JSON Checkpoint 載入狀態。
   * 恢復 Agent Loop 繼續執行直到 Finish(Done)。

最小必要驗證：

* `cargo test --test closed_loop_test at_core_001`
* `cargo test --test closed_loop_test crash_resume`

完成後停止。

# 第六階段：Safe Filesystem Tools

建立基礎檔案系統操作工具，並內建嚴格安全路徑邊界。

範圍：

1. **Tool Trait 抽象**：
   * 定義通用 Tool 介面（名稱、描述、參數 schema、execute）。
   * 執行結果統一回傳 `ActionResult`。
2. **核心檔案工具**：
   * `read_file`
   * `write_file`
3. **安全邊界**：
   * 工作目錄限制（嚴格限制在指定的測試目錄內）。
   * 路徑正規化（canonicalize，嚴防 `..` 目錄穿越攻擊）。
   * 非法路徑拒絕並回傳結構化錯誤。

最小必要驗證：

* `cargo test --test fs_tool_tests`（驗證合法讀寫、目錄穿越攔截、邊界保護）

完成後停止。

# 第七階段：Safe Process Execution

建立安全的系統指令執行工具，隔離子行程風險。

範圍：

1. **指令工具**：
   * `run_command`
2. **行程安全邊界**：
   * 工作目錄綁定。

   * stdout / stderr 長度截斷保護（防止巨大輸出撐爆記憶體）。
   * 結構化退出碼與錯誤分類。

最小必要驗證：

* `cargo test --test process_tool_tests`（驗證正常執行、超時終止、輸出截斷）

# 第八階段：Ollama Provider Adapter

在 Mock 閉環與 Safe Tools 均已完備後，實作對接真實本地 Ollama（`gemma4:26b`）的 Provider Adapter。

範圍：

1. **LLM Provider Trait 實作**：
   * 對接本地 Ollama HTTP API。
   * 支援 model name (`gemma4:26b`)、endpoint、timeout、generation options。
2. **Wire Protocol 映射（ToolCall -> Action）**：
   * 將 Ollama 輸出的 `ToolCall` 解析、驗證並映射轉換為強型別 `Action`，包裝於 `AgentDecision::Act(Action)`。
   * 模型輸出若格式錯誤，由 Adapter 捕捉並回傳結構化錯誤，禁止未經驗證的字串穿透至 Runtime。

最小必要驗證：

* `cargo test --test ollama_adapter_test connectivity_test -- --ignored`
