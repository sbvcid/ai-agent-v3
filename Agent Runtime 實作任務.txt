# Agent Runtime 實作任務

你現在負責將本專案 `01~06 AGENTS.md` 中定義的 Agent Runtime 規格，逐步實作成可運作的程式。

本任務必須遵守專案中的 DEVELOPMENT_WORKFLOW.md。任何 Stage 的執行、checkpoint、狀態更新、中斷恢復與重新接手行為，均以該文件為準。

在開始任何程式修改之前：

1. 檢查專案目錄。
2. 找到並閱讀相關 AGENTS.md。
3. 閱讀 DEVELOPMENT_WORKFLOW.md。
4. 閱讀 IMPLEMENTATION_STATUS.md（如果存在）。
5. 閱讀本實作任務。
6. 檢查 Cargo.toml、source code、tests。
7. 執行必要的 cargo check / cargo test。
8. 判斷目前實際完成到哪個 Stage。
9. 如果文件狀態與實際程式不一致，以實際程式與測試結果為準。
10. 確認目前應該處理的 Stage 後，再開始修改。

目前環境：

* 已安裝 Ollama
* 已有模型：`gemma4:26b`
* Agent Runtime 目前處於開發階段
* `01~06 AGENTS.md` 是目前主要設計規格
* 專案可能已經存在部分 Runtime、Tool、LLM adapter 或測試
* 不要因為實作方便而自行重新設計整套架構
* 優先遵循現有 `AGENTS.md`
* 如果不同規格之間存在衝突、缺漏或歧義，不得自行猜測，必須先指出問題

# 最重要的開發規則：Incremental Implementation

本專案必須採用「一次只完成一個階段」的開發方式。

**禁止一次完成整個 Agent Runtime。**

你必須嚴格按照階段順序工作。

每次只執行目前被指定的階段。

完成該階段後：

1. 編譯
2. 執行該階段相關測試
3. 修正該階段產生的問題
4. 再次執行測試
5. 確認該階段達到驗收標準
6. 回報：

   * 修改了哪些檔案
   * 修改了什麼
   * 為什麼修改
   * 執行了哪些命令
   * 測試結果
   * 是否通過
   * 下一階段準備做什麼

**完成後立即停止。**

不得因為目前階段已完成，就自行繼續實作下一階段。

只有在使用者明確要求「繼續下一階段」後，才能開始下一階段。

---

# 修改範圍控制

每個階段只修改完成該階段所必要的程式。

不要：

* 一次修改整個專案
* 預先實作下一階段
* 為尚未使用的功能建立複雜 abstraction
* 為了測試方便而破壞既有架構
* 將暫時性的 workaround 當成正式架構
* 修改與目前階段無關的程式

如果發現下一階段需要先修改某個目前尚未定義的介面：

先報告問題，不要自行擴張目前階段的範圍。

# 第二階段：Canonical Core Data Model

這一階段只處理 Agent Runtime 的核心資料結構。

先確認並統一必要的核心概念，例如：

* AgentInput
* AgentObservation
* AgentDecision
* ToolCall
* ToolResult
* Finish / FinalResponse
* AgentEvent
* Run / Execution Context

實際名稱必須以 `01~06 AGENTS.md` 最終確定的規格為準。

目標：

**整個 Runtime 必須使用同一套 canonical data model。**

禁止：

* A module 使用 `thought`
* B module 使用 `reasoning`
* C module 使用另一個代表同一概念的欄位

除非規格明確要求它們是不同概念。

這一階段完成後：

* 編譯
* 執行相關 unit tests
* 驗證 serialization / deserialization
* 驗證不同 module 使用相同型別

完成後停止。

特別確認：

* AgentDecision

# 第四階段：Deterministic Mock LLM

建立 Mock LLM。

Mock LLM 不需要真正理解自然語言。

它的目的只是驗證 Runtime。

建立 deterministic scenario，例如：

User：

「建立 test.txt，內容為 hello。」

Mock LLM 第一次固定回傳：

ToolCall：

`write_file("test.txt", "hello")`

Runtime 執行 Tool。

Tool 回傳成功。

Mock LLM 第二次收到 Tool Result 後固定回傳：

Finish：

「完成。」

測試必須實際驗證：

Observe
→ Think
→ Act
→ Observe
→ Think
→ Finish

這一階段不需要 Ollama。

目的：

**證明 Runtime Loop 本身正確，而不是證明 LLM 很聰明。**

完成後：

* 執行 Mock test
* 確認 Tool Call 被正確解析
* 確認 Tool Result 被送回 LLM
* 確認 Finish 能正確結束 loop
* 確認沒有 infinite loop

完成後停止。

---

# 第五階段：最小 Agent Loop

建立通用 Agent Loop。

目標：

User
→ Agent Runtime
→ LLM
→ Decision
→ Tool Call
→ Tool Execution
→ Tool Result
→ LLM
→ Final Answer

Runtime 必須支援：

* user input
* LLM request
* LLM response
* decision parsing
* tool call
* tool execution
* tool result
* 下一輪 decision
* finish

重要：

**不得將 Agent workflow 寫死。**

Runtime 不得假設：

`read_file → write_file → run_python → finish`

也不得假設固定 Tool 順序。

LLM 應該可以決定下一步。

Runtime 只負責：

* 提供 observation
* 呼叫 LLM
* 解析 decision
* 執行 Tool
* 回傳 Tool Result
* 控制 execution lifecycle

完成後使用 Mock LLM 驗證不同 Tool sequence。

例如：

Scenario A：

LLM：

`read_file → finish`

Scenario B：

LLM：

`search_files → read_file → finish`

Scenario C：

LLM：

`run_python → finish`

Runtime 都必須正常工作。

完成後停止。

# 最終架構目標

最終需要能夠真正執行：

User
↓
Agent Runtime
↓
LLM Provider
↓
Ollama
↓
gemma4:26b
↓
AgentDecision
↓
Tool
↓
ToolResult
↓
Agent Runtime
↓
LLM
↓
Final Answer

核心原則：

**LLM 負責決定下一步。**

**Runtime 負責執行決定。**

**Tool 負責操作環境。**

**Observation / Tool Result 負責把環境狀態帶回 Agent。**

不得將 Agent workflow 硬編碼成固定順序。
